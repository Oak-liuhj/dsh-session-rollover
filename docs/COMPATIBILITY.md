# DSH 升级适配与验收

插件按“声明兼容范围、运行前探测、逐版检查、真实宿主验收”维护。安装范围与实机验收记录分别维护；不能提前保证尚未发布的 DSH 一定兼容，也不根据版本号猜测新接口。

## 当前范围

- 历史真实宿主验收基线：`0.2.1-rc.5`；`1.2.0` 已在本机安装的 `0.2.2-rc.1` 独立 home / profile 中完成实机验收。
- `1.2.1` 按维护者指定策略声明 `0.2.1-rc.5 || >=0.2.2-rc.1 <0.3.0-0`，允许范围内后续 RC、正式和补丁版本安装；排除 `0.3.0` 的全部预发布和正式版本。
- DSH 的版本判定使用 `includePrerelease: true`：该范围也包含 `0.2.3-alpha.1` 等后续 0.2.x 预发布版本；普通 SemVer 工具的默认预发布排除规则不同，复核时需使用与宿主相同的选项。`0.2.1` 分支仅保留确切的 `0.2.1-rc.5`。
- `compatibility/policy.json` 的 `supportedRuntimeRange` 决定安装范围，`engines.dsh` 必须与其一致；`verifiedRuntimeVersions` 独立记录已完成实机验收的版本，不再用于拼接安装白名单。
- `verifiedRuntimeVersions` 保留 `0.2.1-rc.5`、`0.2.2-rc.1`；历史证据保留采集时的插件版本，不因扩大范围而修改为新发行版或加入未实测宿主。
- npm 声明扫描、夹具回归和真实宿主验收分别记录。扫描通过不自动修改版本约束，不自动发布 npm 包，也不自动改用户 profile。
- 已安装旧版的用户需更新到包含新兼容声明的插件包；npm 同一版本不会被覆盖更新。历史发布核验记录见 [投稿材料](../marketplace/SUBMISSION.md)。

## 运行保护

服务端集中在 `src/server/compatibility.mjs` 检查会话存储、标题、创建/提示/模型选择、投影、工作区接口，以及同步读取的返回结构。关键能力不满足时，自动与手动分卷在创建会话、改名、保存重试之前停止；HTTP 建卷操作返回 `503 host-incompatible`，面板显示更新提示。

已有的交接快照与只读状态仍可读取；已注册的服务端归档写入拦截不因分卷暂停而关闭。方法存在不证明事件语义仍相同；如果升级导致插件本身无法加载，这些插件内保护也无法运行，所以仍需遵守宿主版本约束。

新版宿主优先通过 `workingDirectory.get(session)` 和活动 Agent 的 `model.current()` 读取领域状态。缺少这些可选服务时，回退到已验证的 `sessionProjections.stateOf`。后者在较新源码中已弃用，仍纳入声明检查；将来移除时明确失败，由维护者适配，而不是静默换成空目录或默认模型。

基线 `0.2.1-rc.5` 的 Agent 声明尚无 `current()`，检查策略对此确切版本保留显式例外，运行时使用投影回退；后续版本继续检查领域服务接口。未知模型结构会暂停分卷，合法的空选择保持可用。

浏览器针对插槽、导航与输入阻塞服务做能力检查。缺少可选界面能力时记录带插件名的警告，并在可用的面板中提示；不让缺失服务直接导致 React 渲染错误。服务端诊断可通过 `ctx.sessionRollover.compatibility()` 获取；每个会话状态的 `compatibility` 还包含返回结构检查。

## 自动检查

仓库工作流 `.github/workflows/compatibility.yml` 包含：

1. Windows / Linux、Node.js 22 / 24 上运行完整回归、发布格式检查和 tgz 隔离安装校验。
2. 从官方 npm 注册表枚举基线发布时刻之后的每个 DSH 版本，包含 alpha、rc 与后续补丁；不只检查 `latest`，避免遗漏中间版本。
3. 下载各版本的十一个公开组件包，核对 SHA512 后只读扫描类型声明，检查插件使用的方法、事件名及界面插槽，并保存报告。不会执行上游安装脚本。

工作流在代码推送、PR、手动触发和每六小时的定时任务中运行；需要提交到 GitHub 默认分支并启用 Actions 才会生效。本地创建文件不等于已启用远程任务。注册表请求或归档校验失败均使任务失败，不视为兼容通过。版本数超过 200 时要求维护基线，不静默截断。

```powershell
npm test
npm run check:release
npm run check:package
npm run check:dsh -- all
npm run check:dsh -- 0.2.2-rc.1
node scripts/check-dsh-compatibility.mjs --list
```

需要网络与系统 `tar`；Windows 自带的 tar 可用。报告默认写入忽略提交的 `out/dsh-compatibility.json`，也可用 `DSH_COMPATIBILITY_REPORT` 指定位置。`level: public-declaration-smoke`、`runtimeVerified: false` 明确说明证据边界。声明扫描不会证明方法签名、授权、事件顺序或视觉渲染完全兼容。

`check:package` 在自有临时目录安装实际 tgz，复核导出、预构建客户端和全部发布资源，结束后清理隔离目录；包与报告保存在 `out/`。此检查也不代表真实 DSH 宿主验收。

## 每次 DSH 发布后的维护步骤

1. 查看每个新版本的声明扫描和回归结果；发现方法、事件或插槽变化时更新集中适配层，保留旧宿主路径的测试。
2. 用该版本的真实 DSH，在隔离 home / profile 和本地模型夹具中验证：插件装载、十条真实用户消息只分一次、模型与工作区继承、待办交接、来源导航、重启恢复、归档只读及恢复写入、HTTP owner 授权。不得使用生产会话验收。
3. 记录 DSH 与插件版本、平台、结果及证据位置。通过后才向 `verifiedRuntimeVersions` 添加确切版本及实机证据，保留证据采集时的插件版本。范围内新增实测版本无需修改 `engines.dsh`；超出范围时需单独审核并同步修改 `supportedRuntimeRange` 与清单。旧基线继续用于回归。
4. 更新插件版本、构建预生成客户端、完成打包与隔离安装验证，再发布新 npm 版本。用户通过正常插件升级获得适配；不得覆盖同一 npm 版本。

宿主升级后遇到兼容提示时，应保留数据目录，使用已验收版本组合或更新插件；不要删除快照、绕过宿主版本检查或同时加载两份插件。
